# 홈페이지 AI 제품 상담 RAG 아키텍처 결정

최종 업데이트: 2026-09-11

상태: V1 구현 완료, 운영 연결 대기

## 결정

- 벡터 검색 DB는 기존 운영 DB와 같은 **PostgreSQL + pgvector**를 사용한다.
- 임베딩 모델은 **BGE-M3**를 사용한다.
- PostgreSQL에서 벡터 청크, 미답변 질문, 승인 Q&A, 원문·버전·색인 상태를 함께 관리한다.

## 이유

홈페이지 제품 상담은 한국어·일본어·영어와 AIP, ACP, Lingo, FDE, MCP 같은 정확한 제품 용어를 동시에 다룬다. 의미가 비슷한 질문을 찾는 dense 검색만으로는 약어·가격·인증명·제품명을 놓칠 수 있고, 키워드 검색만으로는 표현이 달라진 질문을 놓친다.

BGE-M3는 다국어 검색에 적합한 1,024차원 dense 벡터를 제공한다. 현재 정제 후 코퍼스는 2,438청크로 작기 때문에 Qdrant를 별도로 운영하는 이점보다 DB 연결·백업·장애 지점을 하나로 줄이는 이점이 크다. pgvector의 cosine 검색 결과와 기존 다국어 키워드 검색 결과를 애플리케이션에서 RRF로 합쳐, 정확한 제품 용어와 자연어 표현을 함께 처리한다.

현재 사내 GLM 채팅 엔드포인트는 `/v1/chat/completions`은 지원하지만 `/v1/embeddings`는 지원하지 않는다. GLM은 답변 생성에만 쓰고, BGE-M3는 별도 내부 임베딩 서비스로 운영한다.

## 청크 결정

초기 공개·승인 코퍼스 271문서, 2,286개 청크와 16개 대표 질문으로 같은 키워드 점수식을 비교했다. 아래 수치는 당시 실험 기록이며, 현재 정제 후 색인 규모는 2,438개다.

| 방식 | 청크 수 | 정답 출처 Top-1 | 정답 출처 Top-3 | MRR |
| --- | ---: | ---: | ---: | ---: |
| 현재 섹션 단위 | 2,286 | 87.5% | 100% | 0.917 |
| 1,200자 / 160자 중첩 | 2,339 | 87.5% | 100% | 0.917 |
| **800자 / 120자 중첩** | **2,447** | **93.8%** | **100%** | **0.958** |

따라서 V1 색인 청크는 본문 기준 **800자, 120자 중첩**으로 시작한다.

- 각 청크 앞에는 `제품명 · 문서 제목 · 섹션 제목`을 붙인다.
- FAQ는 질문과 답변을 반드시 같은 청크로 보존한다.
- 가격표·표 형식은 행과 열의 의미가 끊기지 않도록 하나의 논리 단위로 보존한다.
- 문서 URL, locale, 제품, 공개 범위, 문서 버전, 수집 시각을 청크 메타데이터에 함께 저장한다.

평가 도구와 질문 세트는 각각 `scripts/ai-chat/evaluate-retrieval.mjs`, `scripts/ai-chat/retrieval-eval-cases.json`에 있다. 새 자료나 청크 전략을 적용하기 전후에 `npm run chat:evaluate-retrieval`로 비교한다.

로컬 PostgreSQL에 BGE-M3 1,024차원 벡터 2,447개를 실제 색인한 뒤 같은 16개 질문으로 평가한 결과는 다음과 같다.

| 검색 방식 | 정답 출처 Top-1 | 정답 출처 Top-3 | MRR |
| --- | ---: | ---: | ---: |
| BGE-M3 dense 단독 | 68.8% | 93.8% | 0.801 |
| **키워드 상위 3개 + BGE-M3 RRF** | **93.8%** | **100%** | **0.958** |

dense 단독은 표현이 바뀐 질문을 찾는 데 유용하지만 정확한 인증명과 일부 ACP 문서의 순위가 낮았다. 따라서 키워드 상위 3개를 정확성 앵커로 유지하고 벡터 검색은 나머지 후보를 보강하는 방식으로 확정했다.

## 검색 흐름

1. 사용자 질문에서 제품과 locale을 추정한다.
2. PostgreSQL에서 제품·locale 필터를 적용하고 BGE-M3 cosine 검색 후보 20개를 가져온다.
3. 정확한 제품명·가격·인증을 보호하기 위해 키워드 상위 3개를 유지하고, 나머지 후보는 벡터 결과와 RRF로 합친다.
4. URL별 최대 3개를 유지하며 답변 모델에는 상위 8개를 보낸다.
5. 답변 모델은 전달된 근거만 사용하고 실제 사용한 출처만 표시한다.

제품이 명시된 질문은 다른 제품의 청크를 섞지 않는다. 다만 LinkPie처럼 AIP Apps 문서에 근거가 있는 제품은 명시적인 소스 매핑을 통해 AIP 문서만 예외적으로 포함한다.

## PostgreSQL 데이터 모델

`ai_chat_knowledge_chunks` 테이블의 한 행은 하나의 청크다.

- `embedding vector(1024)`: BGE-M3 dense vector
- `content`: 답변 모델에 전달할 원문
- `product`, `locale`, `source_visibility`, `document_id`, `source_url`, `heading`, `corpus_version`, `source_collected_at`: 필터·버전 메타데이터
- HNSW cosine 인덱스와 `(product, locale)` 인덱스를 함께 둔다.

JSON 스냅샷과 승인 지식 파일은 기준 데이터이고 벡터 행은 언제든 재생성 가능한 인덱스다. 승인 취소·문서 갱신·삭제 시 `npm run chat:index-knowledge`를 다시 실행하면 현재 `corpus_version`에 없는 행이 제거된다.

## 고객 답변 근거 정제 (2026-09-11)

- 공개 문서 원본 JSON은 보존하고 `src/features/ai-chat/evidencePolicy.ts`에서 답변 사용 가능 본문을 만든다. 미확정 로드맵, 페이지 부속 문구는 검색에서 제외·보류한다. 내부 Slack 리서치와 미승인 제품 기획은 로컬 검토 자료로만 보관하고 이 공개 저장소에는 넣지 않는다.
- 미래 기능이라는 단서만 삭제하지 않는다. 그 단서가 적용되는 문장·행·목록을 함께 보류한다. 현재 기능과 분리 가능한 부분만 원문 그대로 남긴다. Beta 주의사항, 권한 조건, 회의 일정의 ‘예정’은 유지한다.
- 키워드 검색과 임베딩 생성이 같은 정책을 사용한다. 임베딩을 800자 단위로 나누기 **전에** 원본 섹션의 문맥에서 정제한다.
- 벡터 검색 결과는 현재 허용된 전체 섹션의 일부인지 재확인한다. 오래된 색인이나 단서가 잘린 벡터 조각으로 제외 내용이 재유입되는 것을 막는다.
- 색인 갱신은 새 본문 반영과 구버전 행 정리를 하나의 DB 트랜잭션으로 처리한다. 원본에서 보류 내용을 복구할 수 있다.
- `node scripts/ai-chat/audit-evidence.mjs`로 제외·보류 사유, 원문, 남긴 본문을 조회할 수 있다. 정책 변경 뒤 `npm run chat:index-knowledge`를 실행한다.
- 사용자가 물은 단일 기능을 확인할 수 없으면 일반 제품 소개를 덧붙여 답변 완료로 처리하지 않고 `insufficient_evidence`로 분류하도록 요청한다. 과거 대화의 답변은 사실 근거로 사용하지 않는다.
- Lingo와 AIP의 업무 연계 질문은 기존 Lingo MCP 개요·연결 절차를 먼저 제공해, 정확한 자료가 있는데도 미답변 처리하는 일을 줄인다.

공개 저장소 기준: 원본 2,300개 섹션 중 17개는 전체 보류/제외, 22개는 일부 정제, 2,261개는 그대로 유지한다. 내부 검토용 2개 섹션은 공개 파일에서 제외했다. 답변 근거는 기존과 같은 2,283개 섹션이며 임베딩은 2,438개다. 검색 평가 스크립트의 과거 키워드 점수식은 실제 서비스와 차이가 있으므로 고객 답변 검증에는 실제 서비스 검색 함수를 사용한다.

## 구현 전제와 다음 단계

1. 운영에서는 pgvector 확장을 지원하는 관리형 PostgreSQL 연결값을 `AI_CHAT_DATABASE_URL`에 설정한다.
2. Vercel 서버에서 접근 가능한 TLS 기반 BGE-M3 OpenAI 호환 endpoint를 준비한다. 로컬에서는 Docker의 Ollama를 사용한다.
3. 배포 전 `npm run chat:setup-database`와 `npm run chat:index-knowledge`를 실행한다.
4. 현재 16개 평가 질문을 50개 이상으로 늘리고, 키워드·dense·hybrid RRF 결과를 같은 표로 비교한다.
5. 운영 임베딩 endpoint 장애 시 키워드 검색으로 자동 fallback하며, 장애 원인은 서버 로그로 확인한다.
