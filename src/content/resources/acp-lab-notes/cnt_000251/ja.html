参照内容を報告書に使う場面がある。配送集計や金額比較にはファイルが便利だが、誰が何を何のために取得したかも管理したい。

 

今回はQueryPieの SQL Export Requestで注文概要を出力した。開発者がSQLと理由を提出し、承認後に取得した。申請・承認・実行結果までWorkflowで確認できた。

 

Community Editionに接続した架空注文DBを使用し、実際の顧客情報は使っていない。

 

 

1. 報告書に必要な項目だけを選ぶ

 

今回は注文3件の配送状況報告だ。必要なのは番号・状態・金額で、名前や連絡先は不要なので対象列から除外した。

 

ordersからorder_id、status、total_amountだけを選び、4001〜4003を対象にするSQLを書いた。

 

SELECT order_id, status, total_amount
FROM orders_control.orders
WHERE order_id BETWEEN 4001 AND 4003
ORDER BY order_id;

 

範囲をSQLにすれば、「注文データが必要」という説明だけより承認者が具体的に確認しやすい。

 

 

2. 承認者とファイルを受け取る人を決める

 

Approval RulesでOrders Lab - Export Approvalを作り、SQL Export Requestを指定した。

 

承認者をDemo Approver、実行者をDemo Developerにした。開発者が申請し、承認後に出力する。自己承認は許可しなかった。

 

 

ダウンロードにも役割を設定でき、確認担当と資料利用者を業務に合わせて分けられる点がよかった。

 

 

3. SQLと利用目的をまとめて提出する

 

開発者でWorkflowのSQL Export Requestを開くと、作った規則どおりに承認者と実行者が表示された。

 

「配送状況報告のための注文概要出力」とし、Orders Control Lab、orders_control、Query ResultでSQLを入力した。承認・実行期限は当日にした。

 

 

理由には番号・状態・金額だけが必要で、名前・電話・メールは含めないと記載した。提出後はIn Progressで承認も実行もPendingだった。

 

 

 

4. 承認者は実際に出力するSQLを確認する

 

Demo ApproverのReceived RequestsでSQL、業務理由、実行期限を確認した。

 

 

連絡先が含まれないことを確認して承認し、配送報告目的の出力を許可し、連絡先非包含を確認したとコメントした。

 

承認記録に目的とSQLが残り、後から出力理由を調べる際も申請から確認できる。

 

 

5. 取得したファイルには申請した注文3件が入っていた

 

開発者でExecutions → To Doの承認済み申請を開き、ExecuteからCSVと先頭行の列名付与を選んだ。

 

ダウンロードが完了し、Resultsには 3 Rows selectedという結果が残った。

 

 

ZIP内のexport.csvを開くと先頭はorder_id、status、total_amountで、下に4001・4002・4003の状態と金額があった。申請した三列・三件がそのままファイルになった。

 

 

実行後はExecutionsのDoneに移り、状態は Successとなり、申請者と申請・更新時刻も表示された。

 

 

 

6. 資料を受け取る業務にも確認できる記録ができた

 

SQL Export Requestはファイル作成前後の業務をつなぐ。利用者がSQLと理由を出し、承認者が内容を確認し、実行者は承認済み申請から取得できた。

 

導入担当者にも説明しやすい。 誰が何を申請し、誰が承認し、実行が成功したかを申請と結果の画面で追えるからだ。

 

注文3件のCSVという小さな作業でも、出力に承認と実行記録を付けられると確認できた。報告書作成のような日常DB業務をQueryPieで管理する姿が見えた。
