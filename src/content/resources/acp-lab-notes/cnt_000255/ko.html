지난 글에서는 주문 분석팀 그룹을 만들고, 새 담당자를 추가해 DB를 조회해봤다. 설정이 잘 적용되는 것을 확인하고 나니 한 가지가 더 궁금했다. 나중에 다른 담당자가 이 환경을 넘겨받으면, 지금의 권한이 어떻게 만들어졌는지도 알 수 있을까.

 

이번에는 QueryPie의 감사 메뉴에서 내가 조금 전 했던 작업을 찾아봤다. 그룹을 만든 기록, DB 권한을 부여한 기록, 사용자를 그룹에 추가한 기록을 차례로 확인했다. 운영 중 “이 권한은 누가 줬나요?”라는 질문을 받았을 때 어디서 답을 찾을 수 있는지 살펴본 셈이다.

 

 

1. 관리자 작업도 기록으로 남아 있었다

 

관리자 화면에서 Audit → General → Activity Logs를 열었다. 사용자와 그룹을 만든 기록뿐 아니라, 앞선 실습에서 설정한 승인 규칙과 보안 정책 관련 작업도 목록에 보였다.

 

각 행에는 작업 시각, 작업 종류, 대상, 작업자, 이메일, 접속 IP가 표시됐다. 사용자가 실행한 SQL뿐 아니라 관리자 설정 작업도 나중에 찾아볼 수 있다는 점이 좋았다.

 

 

 

2. 그룹 이름으로 필요한 기록을 좁혔다

 

검색 기준을 Target으로 두고 Orders Lab - Analysts를 입력했다. 주문 분석팀에 해당하는 기록만 남았고, User Group Created와 Group Member Added 두 작업이 나타났다.

 

대상 이름을 알고 있으니 전체 로그를 하나씩 훑어볼 필요가 없었다. 팀이나 정책 이름을 알아보기 쉽게 정해두면, 이런 화면에서 나중에 기록을 찾을 때도 도움이 되겠다.

 

 

그룹 생성 기록의 상세도 열어봤다. 2026년 11월 8일 17:48:45에 Admin이 그룹을 만들었다는 정보와 함께, Affected Data에 생성한 그룹 이름과 인증 제공자 QueryPie가 표시됐다.

 

 

 

3. 누가 팀에 추가됐는지도 확인할 수 있었다

 

이번에는 Group Member Added 기록을 열었다. 작업 시각은 17:52:40, 작업자는 Admin이었다. 아래 Affected Data에는 그룹 이름 Orders Lab - Analysts와 사용자 이름 Demo Analyst가 남아 있었다.

 

그룹을 수정했다는 사실만 남는 것이 아니라, 어느 사용자가 추가됐는지까지 확인할 수 있었다. 사용자가 늘어나거나 운영 담당자가 바뀌어도, 구성원이 추가된 경위를 기록으로 설명할 수 있겠다.

 

 

 

4. DB 권한을 부여한 기록도 찾았다

 

DB 접근 권한 이력은 Audit → Databases → Access Control Logs에서 확인했다. 이 목록에는 Access Control Granted와 Access Control Revoked 같은 이벤트가 표시됐다.

 

지난 실습에서 사용한 개발자 계정의 권한 부여와 회수 기록도 보였다. 이번에는 Name 검색으로 주문 분석팀 그룹의 기록을 찾았다.

 

 

검색 결과에는 17:49:40의 Access Control Granted 기록 한 건이 나왔다. User Type은 GROUP, 권한 이름은 Read-Only였다. 개인 사용자에게 직접 준 권한인지, 그룹에 준 권한인지도 구분할 수 있었다.

 

 

가로로 이어지는 항목을 확인하니 권한은 Select, 대상 연결은 Orders Control Lab, DB 호스트는 orders-db였고 Action By에는 Admin(2)이 표시됐다. 누구에게 어떤 DB 권한을 부여했는지 구체적으로 확인할 수 있었다.

 

 

 

5. 세 기록을 모으니 권한이 생긴 과정이 보였다

 

이번에 찾은 기록을 시간순으로 정리하면 다음과 같다. 모두 같은 날 내가 진행한 실습이다.

 

  • 17:48:45 — 주문 분석팀 그룹 생성

  • 17:49:40 — 그룹에 Orders Control Lab의 Read-Only 권한 부여

  • 17:52:40 — Demo Analyst를 그룹 구성원으로 추가

 

지난 글에서 분석 담당자가 주문을 조회할 수 있었던 이유가 이 기록과 연결됐다. 읽기 전용 DB 권한이 있는 그룹에 사용자가 추가됐기 때문이다. 현재 설정을 보는 것과 그 설정이 만들어진 과정을 확인하는 것이 함께 가능했다.

 

 

6. 권한을 관리하는 일에 설명할 근거가 생겼다

 

도입 담당자는 권한을 잘 부여하는 것만큼, 나중에 그 권한을 설명할 수 있는지도 신경 쓰게 된다. 보안 점검 때는 누가 언제 설정했는지 묻게 되고, 운영을 넘겨받을 때는 어떤 과정을 거쳐 현재 상태가 됐는지 궁금해진다.

 

직접 찾아보니 QueryPie에는 그 질문에 답할 기록이 남아 있었다. 그룹 이름으로 작업을 찾고, 상세에서 추가된 사용자를 확인하고, DB 권한 로그에서 대상 연결과 허용 범위를 확인할 수 있었다.

 

권한을 설정하는 기능과 그 설정을 추적하는 기록을 함께 제공한다는 점이 이번에 눈에 들어왔다. 여러 담당자가 함께 운영하는 환경에서도 기억에만 의존하지 않고 작업 이력을 확인할 수 있어, 관리 업무에 도움이 되겠다는 생각이 들었다.
