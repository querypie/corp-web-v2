最初は一人に権限を与えれば十分だった。同じ業務の人が増えると、個人別の権限確認は煩雑になりそうだ。

 

QueryPieで注文分析チームを作り、読み取り専用を定めて新担当者を追加した。個別付与なしで参照できるか確認した。

 

 

1. 注文分析チームのグループを作る

 

General → User Management → GroupsのCreate Groupで、注文状況を見る架空チームOrders Lab - Analystsを作った。

 

Demo Analystも用意した。グループ追加による変化を見るため、個人へのDB権限は付けなかった。

 

 

 

2. チームに必要な権限を先に決める

 

Databases → DB Access Control → Access Controlでグループを選び、Orders Control LabのRead-Onlyを付与した。

 

注文分析ならまず参照だ。変更まで一括で許可せず、業務に合わせて読み取り専用にした。

 

 

保存後はグループの一覧に接続とRead-Onlyが表示され、チームが使うDBと権限が一目で分かった。

 

 

 

3. 加入前は接続できるDBがない

 

加入前にDemo AnalystでDatabasesを開くと、 There are no available connections!と表示された。アカウント作成だけではDBを使えなかった。

 

ユーザー登録と業務用DB権限は別だった。アカウントを先に準備し、担当業務に応じてチームを決める運用が考えられる。

 

 

 

4. 分析チームに担当者を追加する

 

管理者でOrders Lab - Analystsを開き、Add UsersでDemo Analystを追加して保存した。個人へのDB権限再付与はしていない。

 

 

構成員一覧にDemo Analystが表示された。権限と構成員を分けて管理でき、同じ業務に同じ基準を適用しやすそうだ。

 

 

 

5. グループ権限で参照でき、変更は止まる

 

再ログインするとOrders Control Labが見え、詳細の権限名は Read-Only (Orders Lab - Analysts)と表示された。

 

権限の有無だけでなく、どのグループ由来かも分かった。「なぜ接続できるか」を説明する根拠になる。

 

 

ConnectでWeb SQLエディターを開き、番号・状態・金額を参照した。

 

SELECT order_id, status, total_amount
FROM orders_control.orders
ORDER BY order_id;

 

4001〜4003の3件が正常に返った。グループに定めた権限だけで新担当者が業務を始められた。

 

 

データを変えず制限を確認するため、存在しない番号-1を条件にUPDATEした。QueryPieは No permission to execute UPDATE statementというメッセージで遮断した。

 

 

 

6. チームが増えるほど役立ちそうだ

 

権限の基準が明確になった点がよかった。チームに必要なDBと権限を決め、業務担当者を追加すればよい。

 

導入では最初の接続成功だけでなく、利用者増加後も一貫して管理できることが大切だ。チーム権限、構成員、ユーザー権限の出所を確認できる点が印象的だった。

 

一人の追加でも、チーム単位の権限運用を理解できた。 必要な参照を許可し、変更は防ぐ基準をグループに定めること。 QueryPieを組織全体へ広げたい担当者に役立つ機能だ。
